HTML/CSS/JS를 처음 배우면 용어와 규칙이 쏟아져서 일단 외우고 넘어가기 쉽다. 근데 "왜 이렇게 되어있을까"를 한 번 짚고 넘어가면 훨씬 오래 기억에 남는다. 그 관점으로 정리해봤다.

## HTML

### 왜 태그가 이렇게 많이 나뉘어 있을까?

HTML은 원래 "문서"를 표현하려고 만들어진 언어다. 논문이나 책처럼 제목, 문단, 목록, 표 같은 구조가 있고, 그 구조마다 다른 태그를 쓴다. 즉 태그를 고르는 기준은 "화면에 어떻게 보이게 할까"가 아니라 "이 내용이 무슨 역할을 하는가"다. 이 관점 하나만 있어도 태그를 외울 때 훨씬 헷갈리지 않는다.

### 왜 눈에 안 보이는 태그(meta, link, script)가 필요할까?

브라우저는 화면을 그리기 전에 "이 문서를 어떻게 다뤄야 하는지" 알아야 한다. `<meta>`는 문자 인코딩이나 검색엔진 노출 같은 문서 자체의 정보를 알려주고, `<link>`와 `<script>`는 각각 CSS/JS 파일을 어디서 가져올지 알려준다. 화면에 안 그려지는 게 아니라, 화면을 그리기 위한 준비 작업이라고 보면 된다.

### 왜 id와 class를 구분해서 쓸까?

`id`는 "이 페이지에 딱 하나뿐인 요소"를 가리킬 때, `class`는 "같은 스타일/동작을 공유하는 여러 요소"를 가리킬 때 쓴다. 버튼 100개에 똑같은 디자인을 입히고 싶으면 class, 페이지 안에서 딱 하나뿐인 로그인 폼을 JS로 콕 집어 다루고 싶으면 id — 이렇게 "몇 개를 가리킬 것인가"로 구분하면 된다.

### 왜 블록 요소와 인라인 요소가 나뉠까?

문단(`<p>`)처럼 한 덩어리로 취급돼야 하는 내용과, 문장 중간에 강조 표시(`<strong>`)처럼 흐름을 끊지 않아야 하는 내용은 레이아웃 방식이 다를 수밖에 없다. 그래서 블록 요소는 줄 전체를 차지하고, 인라인 요소는 내용 크기만큼만 차지한다.

### 왜 img 대신 picture를 쓰기도 할까?

모바일에서 데스크탑용 큰 이미지를 그대로 불러오면 로딩만 느려지고 화질 이득도 없다. `<picture>`는 화면 크기에 맞는 이미지를 골라 불러올 수 있게 해준다 — 즉 "화면마다 다른 그림을 보여주고 싶다"는 필요 때문에 생긴 태그다.

### 왜 시맨틱 태그(header, nav, footer...)를 써야 할까?

`<div>`만으로도 화면은 똑같이 나온다. 문제는 사람이든 기계든 그 `div`가 뭘 하는 영역인지 이름만 봐서는 모른다는 점이다. 시맨틱 태그를 쓰면 코드를 읽는 사람도, 검색엔진도, 스크린리더도 "여기가 내비게이션이구나"를 바로 알 수 있다. 결국 접근성과 유지보수를 위한 선택이다.

### 왜 반응형 웹이 필요할까?

같은 웹페이지를 폰, 태블릿, 모니터에서 다 열어본다. 픽셀 값을 고정해두면 작은 화면에서는 잘리고 큰 화면에서는 텅 비어 보인다. 그래서 `viewport` 메타 태그로 "이 기기의 실제 너비를 기준으로 삼아라"라고 알려주고, 크기는 `%`나 `vw`처럼 상대 단위로 지정한다.

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

## CSS

### 왜 CSS를 적용하는 방법이 3가지나 있을까?

Inline(요소에 직접), Internal(head 안에), External(별도 파일) 세 가지 모두 결과는 같지만, 성격이 다르다. 딱 한 요소에만 급하게 스타일을 넣고 싶으면 Inline이 빠르고, 스타일을 여러 페이지에서 재사용하고 유지보수하려면 External이 낫다. 실무에서 External을 기본으로 쓰는 이유는 "스타일과 구조를 분리해두면 나중에 디자인만 바꾸기 쉽기 때문"이다.

### 왜 셀렉터에 `:`와 `::`가 따로 있을까?

`:hover`처럼 콜론 하나는 "요소의 특정 상태"를 가리키고(마우스가 올라간 상태 등), `::before`처럼 콜론 두 개는 "요소 안에 원래 없던 내용을 새로 만들어 넣는 것"을 가리킨다. 성격이 다른 두 가지를 구분하려고 표기법도 다르게 만든 것이다.

### 왜 transform과 transition을 따로 쓸까?

`transform`은 "모양을 어떻게 바꿀지"만 정의하고, `transition`은 "그 변화가 얼마나 부드럽게 일어날지"를 정의한다. 즉 하나는 결과, 하나는 과정을 담당한다. 그래서 둘을 같이 써야 "마우스를 올리면 버튼이 부드럽게 커진다" 같은 효과가 나온다.

```css
.box {
  transition: transform 0.2s ease; /* 과정 */
}
.box:hover {
  transform: scale(1.05); /* 결과 */
}
```

### 왜 CSS 변수를 쓸까?

브랜드 색상 하나를 버튼, 링크, 배경 등 20군데에 하드코딩해두면, 색을 바꿀 때마다 20군데를 다 찾아 고쳐야 한다. `--main-color` 하나로 값을 선언해두고 `var()`로 불러 쓰면, 값 하나만 바꿔도 전체에 반영된다. "값을 한 곳에서 관리하고 싶다"는 문제를 해결하려고 생긴 기능이다.

```css
:root {
  --main-color: #3459e6;
}
button {
  color: var(--main-color);
}
```

## JavaScript

### 왜 var 대신 let/const를 쓰라고 할까?

`var`는 블록({ }) 안에서 선언해도 함수 전체 범위로 새어나간다. `if` 문 안에서 선언한 변수가 밖에서도 접근되는 식이라, 큰 코드에서는 어디서 값이 바뀌었는지 추적하기 어려워진다. `let`/`const`는 딱 그 블록 안에서만 유효해서 실수를 줄여준다. 그래서 지금은 재할당이 필요 없으면 `const`, 필요하면 `let`을 쓰고 `var`는 잘 안 쓴다.

| 키워드 | 범위 | 재할당 | 재선언 |
|---|---|---|---|
| var | 함수 범위 | 가능 | 가능 |
| let | 블록 범위 | 가능 | 불가능 |
| const | 블록 범위 | 불가능 | 불가능 |

### 왜 `==` 대신 `===`를 쓰라고 할까?

`==`는 비교 전에 타입을 몰래 바꿔버린다. `0 == '0'`도 `true`가 되고, `'' == false`도 `true`가 된다. 이런 자동 형변환 규칙을 다 외우고 있지 않은 이상 예상 못 한 버그로 이어지기 쉽다. `===`는 타입까지 같아야 참이라, "내가 의도한 대로만 비교된다"는 확신을 준다.

### 왜 for...in과 for...of가 따로 있을까?

객체는 "키가 있는 데이터"이고 배열은 "순서가 있는 데이터"라서, 순회하고 싶은 대상이 다르다. `for...in`은 객체의 키를 돌고, `for...of`는 배열이나 문자열처럼 순서가 있는 값을 돈다. 배열에 `for...in`을 쓰면 인덱스가 문자열로 나오는 등 예상과 다르게 동작할 수 있어서, 배열은 `for...of`(또는 `map`/`forEach`)를 쓰는 게 안전하다.

### 왜 객체를 함수에 넘기면 원본이 바뀔 수 있을까?

숫자나 문자열 같은 원시 타입은 함수에 넘길 때 값이 통째로 복사된다(call by value) — 그래서 함수 안에서 바꿔도 원본은 그대로다. 반면 객체나 배열은 "어디에 있는지 주소"가 전달된다(call by sharing). 그래서 함수 안에서 객체의 프로퍼티를 바꾸면 원본에도 반영되지만, 매개변수 자체를 다른 객체로 통째로 바꿔치기하는 건 원본에 영향을 주지 않는다. 이 차이를 모르면 "분명 안 건드렸는데 원본이 바뀌었다" 같은 버그를 만나게 된다.

```js
function addItem(list) {
  list.push('new'); // 원본 배열이 그대로 바뀐다
}
const items = ['a', 'b'];
addItem(items);
console.log(items); // ['a', 'b', 'new']
```

### 왜 호이스팅과 TDZ를 알아야 할까?

JS 엔진은 코드를 실행하기 전에 변수/함수 선언을 미리 읽어들인다(호이스팅). `var`는 이때 `undefined`로 초기화까지 끝내버려서, 선언 위치보다 위에서 써도 에러 없이 `undefined`가 나온다 — 이게 오히려 버그를 조용히 숨긴다. `let`/`const`는 선언 전까지는 아예 접근을 막아버리는데(Temporal Dead Zone), 이건 "선언되지 않은 변수를 쓰는 실수"를 에러로 바로 알려주기 위한 안전장치다.

### 왜 addEventListener를 권장할까?

이벤트를 등록하는 방법은 세 가지다.

1. HTML 속성 방식 (`<button onclick="...">`)
2. DOM 프로퍼티 방식 (`el.onclick = ...`)
3. `addEventListener`

1번과 2번은 한 요소에 핸들러를 하나만 붙일 수 있어서, 나중에 다른 코드가 같은 이벤트를 또 등록하면 앞의 것이 덮어써진다. `addEventListener`는 여러 핸들러를 동시에 등록할 수 있고, 필요할 때 `removeEventListener`로 제거도 가능하다. 여러 스크립트가 같은 요소를 다뤄야 하는 실제 서비스에서는 이 차이가 꽤 중요해진다.

```js
const button = document.querySelector('#save');
button.addEventListener('click', () => {
  console.log('저장됨');
});
```

---

결국 문법 하나하나는 "이런 문제를 겪었는데 그걸 이렇게 풀었다"는 결과물이다. 왜 이렇게 만들어졌는지를 알면, 새로운 문법을 만나도 "아 이것도 이런 문제를 풀려고 있는 거구나" 하고 훨씬 빨리 이해가 된다.
